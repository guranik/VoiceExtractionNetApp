Это система по распределенному преобразованию wav-файлов в текстовые - содержащие транскрипцию речи из исходного.
Клиент должен быть WPF, а воркер и менеджер - консольные проекты.

Для реализации распределенного взаимодействия должен использоваться самописный протокол TCP с помощью System.Net.Sockets. По этому протоколу менеджер и воркер обмениваются сообщениями - в том числе и содержимым файлов (должны быть разные типы сообщений с Json-сериализацией и преобразованием содержимого Wav-файлов в base64-строки)
Менеджер и каждый из воркеров запускаются отдельно от менеджера. 
И еще все проекты могут запускаться на разных компьютерах - но все Windows 10.
Еще, аксиома - при отправке сообщений A -> B, порядок сообщений, в котором их отправляет сетевой узел A всегда идентичен тому, в котором их получает сетевой узел B.

Менеджер ведет учет воркреров с помощью List<WorkerInfo>, где есть в полях TcpClient, общее количество потоков extract и transcribe, количество свободных потоков и методы для обновления этих значений с помощью инкремента и декремента с выбрасыванием исключений. Там еще должен быть метод Dispose, в котором закрывается TcpClient воркера.

У воркеров есть IP менеджера (127.0.0.1), по которому, когда они запускаются, они отправляют WorkerHello, который содержит параметры extract и transcribe - количество .py-потоков каждого типа. 
Если менеджер не получает HeartBeat от воркера секунд 15, он закрывает с ним соединение, что значит - воркер должен будет отправить WorkerHello менеджеру чтобы с ним опять открылось соединение. 
Когда воркер понимает, что соединение с ним закрыто - он выполняет свою полную очистку:
1. посылает сообщение об отмене всем .py-потокам и
2. когда все потоки сообщили об отмене своей обработки, удаляет все файлы из папок extract_segments, transcribe_segments и transcriptions.
3. начинает заново отправлять менеджеру WorkerHello и затем HeartBeat

И менеджер, и воркеры запускаются через dotnet run из их рабочих папок. При запуске они должны проверять(и создавать папки или выбрасывать исключения если файлов нет).
Менеджер проверяет наличие у себя папок input, extract_segments, transcribe_segments, transcriptions.
Клиент тоже содержит ip менеджера по которому подключается к нему.
Воркеры должны проверять наличие папок extract_segments, transcribe_segments, transcriptions. А еще наличие файлов C:\Projects\VoiceExtraction\speech_extractor.py и C:\Projects\VoiceExtraction\speech_transcriptor.py

Воркеры запускают speech_extractor.py-потоки в количестве extract, и speech_transcriptor.py-потоки в количестве transcribe. Воркер хранит ссылки на все потоки - для обращения к ним используется класс PythonWorker.
speech_extractor.py запускается с параметрами --input-dir <split-segments-dir> --output-dir <transcribe-segments-dir> --max-duration <max-segment-duration-sec>. input-dir должен быть <WorkerRoot>/split-segments; output-dir должен быть <WorkerRoot>/transcribe-segments;
speech_transcriptor.py запускается с параметрами --input-dir <transcribe-segments-dir> --output-dir <transcriptions-dir> --model <whisper-model>. input-dir должен быть <WorkerRoot>/segments; output-dir должен быть <WorkerRoot>/transcriptions;
.py-потоки общаются с Воркерами через stdin/stdout/stderr. После запуска скрипта они инициализируют свои модели для обработки. После полной загрузки весов в память и завершения инициализации .py-потоки отправляют своим воркерам сообщения "READY" в stdout. Воркер ведет учет количества этих полученных сообщений и, когда оно равно extract+transcribe, воркер шлет менеджеру сообщение WorkerHello.
при завершении обработки файлов .py-потоки удаляют входной файл и пишут Done в stdout. Перед сохранением файлов в выходные папки .py-потоки добавляют префикс i_ ко всем своим выходным файлам, где i - это индекс .py-потока определенного типа в воркере - их задает 

У обработки файла есть 4 этапа:
1. Алгоритм дробления:
Когда пользователь посылает задачу, менеджер кладет ее в папку input.
Из appsettings.json извлекаются переменые MaxSegmentDurationSec и SplitTranscribeRatio. Затем происходит цикл: 
пока от файла не остался кусок, который меньше, чем MaxSegmentDurationSec * SplitTranscribeRatio * 2 - от него отрезается кусок от начала - длиной MaxSegmentDurationSec * SplitTranscribeRatio. 
Каждый из таких вырезанных кусков и оставшийся "Хвост" файла помещаются в папку extract_segments.
Им дается следующий нейминг: <extract_segment_start>.wav.
Здесь extract_segment_start - время начала сегмента в исходном файле. Оно должно быть формата hh-mm-ss.
2. Алгоритм извлечения речи:
Воркеры получают сообщение о задаче на извлечение в виде класса с названием файла, типом задачи, содержанием файла в виде string base64.
Воркеры помещают этот файл в папку "extract-segments" и выдают задачу потоку speech_extractor.py, который извлекает сегменты, содержащие речь.
Поток скидывает результаты в папку "transcribe_segments" в виде файлов с названиями формата <i>_<segment_start>_<segment_duration>.wav.
Здесь segment_start формата hh-mm-ss-mmm и segment_duration формата hh-mm-ss-mmm, оба имеют 3 цифры для миллисекунд, <i> - это индекс .py-потока. 
Воркер получает DONE из stdout .py-потока и находит файлы, у которых в префиксе <i>_ содержится именно индекс .py-потока.
Этот префикс представлен в виде одного неотрицательного int-числа, которое отделено от остального файла "_".
Нужно так же учесть, что могут быть файлы формата <segment_start>_<segment_duration>.wav. Нужно составить правильное regex-выражение для получения выходных файлов конкретного потока.
Формируется сообщение где есть список всех содержаний файлов, префикс имени которых содержит соответствующий .py-потоку индекс (содержание записывается в виде строки в base64-формате) и список названий этих файлов, из названия которых, перед добавлением в сообщение, удаляется префикс "<i>_".
Так же в сообщении указывается название входного файла .py-потока - SourceFileName.
Затем удаляются файлы, с индексом потока в префиксе, соответствующему обрабатывающему потоку этой задачи, из папки transcribe_segments.
Нужно учесть, что в результате обработки файла .py-потоком может не оказаться выходных файлов - если в аудио не было речи.
Менеджер, получив сообщение TaskMessage, удаляет из папки extract_segments файл, соответствующий по названию SourceFileName.
Файлы из списка в сообщении кладутся в папку "transcribe-segments" и добавляются в очередь transcribe.
3. Алгоритм транскрибации:
Сообщения задач о транскрибации содержат название и содержание файла в base64, полученные от воркеров в результате алгоритма извлечения речи.
Воркер, получив такое сообщение, кладет файл в папку "transcribe-segments" и обрабатывает его потоком speech_transcriptor.py. 
После завершения обработки .py-потоком, получившийся .txt файл, у которого будет тот же нейминг что и у входного файла, за исключением расширения .txt а не .wav, и у которого будет префикс "<i>_" - кладут в папку "transcriptions" и отправляют менеджеру(тоже удалив префикс потока из названия), и, затем, воркер удаляет уже этот выходной файл из папки transcriptions. 
Менеджер результаты транскрипции сохраняет в папке transcriptions, находит файл с таким же названием но с расширением .wav в папке transcribe_segmetns и удаляет его.
4. После завершения всех экстракций и транскрибаций менеджер собирает все файлы транскрипций в единый файл заполняя его содержанием формата: [<transcription_file_name>]: transcription_file_contents \n
После дает файлу название совпадающее с исходным - из папки input. 
Удаляет файл из папки input
Отправляет файл клиенту и после этого удаляет файл из папки output и вручную очищает все свои очереди после чего он готов снова принимать файлы от клиента.

При получении сообщения TaskMessage от воркера менеджер отправляет сообщение о прогрессе клиенту.
У менеджера есть очередь входящих сообщений, и, после выполнения 1 этапа(дробления, который менеджер осуществляет средствами NAudio) читает сообщения из очереди.
Еще должен быть отдельный поток(вернее, 2 потока - для каждого типа задач), который будет отправлять задачи воркерам, у которых имеются свободные потоки, удаляет задачу из очереди и обновляет объект воркера, вызывая метод декремента потоков соответствующего типа. 
Правда, для этого нужно будет внедрить какие-нибудь примитивы синхронизации: использование lock в методах инкремента и декремента обоих типов потоков и использование ConcurrrentQueue для обоих видов задач
